# Прозрачные графы автоматизаций

Встроенные сценарии после V64 состоят из видимых шагов: настройки → данные → оценка → условия → действия.
Пороги, окна поиска, вопросы Jev, правила выбора и тексты сообщений находятся в графах.

## Как изменить сценарий

1. Откройте нужную автоматизацию и выберите этап «Настройки» над холстом.
2. Нажмите блок «Настройки сценария». У каждого значения есть название и пояснение: меняйте число, флаг или список.
3. Выберите этап, который нужно доработать. У каждого блока есть собственное название, этап и пояснение.
4. Выберите тематический блок в панели «Узлы»: например «Отправить сообщение клиенту», «Добавить внутренний комментарий», «Создать заявку» или «Изменить заявку». Поиск над списком находит блоки по названию; каждый шаг находится в одной группе.
5. Укажите параметры. «Текст» — постоянное значение или шаблон; «Скрипт» — выражение с полем события или переменной предыдущего шага; «Из справочника» — конкретный сервис, линия, тип, приоритет или сотрудник. Для чисел, флагов, объектов и списков редактор показывает соответствующие способы ввода.
6. В «Сохранить результат как» задайте имя, например `recommendation`. Поля результата описаны под операцией и доступны в подсказках.
7. Добавьте условие. В редакторе можно выбрать сравнение, сгруппировать условия как «все» или «хотя бы одно», проверить наличие значения или пустоту списка.
8. Соедините «Готово» со следующим шагом и отдельно определите действие на «Ошибка». Изменения применяются после сохранения сценария.

Например, изменение порога приоритета выполняется в настройках сценария «Приоритет (Jev)». Вопрос к Jev редактируется в шаге «Получить рекомендацию по приоритету». Применение рекомендации — отдельный шаг, его можно заменить уведомлением или дополнительным согласованием.

Тематические шаги используют общий формат `OPERATION`: назначение задаётся `config.operation`, параметры — `config.arguments`. Подписи, группы, значки, справочники и типы параметров приходят из `automation/operations.json`. Прежний общий блок «Операция из каталога» заменён прямым выбором действия. Его можно заменить в настройках кнопкой «Заменить шаг»; просмотр другой группы сам по себе не меняет текущий блок.

«Скрипт команд» находится в группе «Дополнительно: скрипты» и сохраняет формат `ACTION` для совместимости. Прежние блоки `CREATE_TASK`, `ESCALATE` и `NOTIFY` продолжают выполняться и поддерживают константы или выражения `=…` в своих значениях. У `CREATE_TASK` по-прежнему сохраняется ID созданной заявки, а у нового `task.create` — объект заявки. Старые графы и их результаты не преобразуются автоматически. Пояснение на холсте (`NOTE`) и внутренний комментарий клиенту (`client.note`) — разные действия.

В «Изменить заявку» можно задать несколько полей, включая исполнителя и линию поддержки. Отдельные шаги добавления/удаления тега и назначения наименее загруженного сотрудника используют те же доменные API и квитанции повторного выполнения, что и остальные записи графа. Эскалация в новом графе задаётся явно: изменение линии/приоритета, снятие исполнителя и при необходимости отдельное уведомление. Стандартные шаблоны используют тематические шаги с выходами успеха и ошибки.

## Данные и результаты

Событие предоставляет `task`, `client`, `message` или `service`/`problem` для мониторинга. Данные других сущностей загружаются отдельными операциями.

Источник сообщения доступен как `message.fromSource` (сообщение, запустившее событие) и `client.lastMessage.fromSource` (последнее по дате и ID сообщение клиента на момент обновления контекста). Значения: `TELEGRAM`, `WHATSAPP`, `EMAIL`, `PORTAL` — личный кабинет, `INTERNAL` — внутренний комментарий. Источник хранится отдельно у каждого сообщения и возвращается также шагом «Получить сообщения клиента». Для старых сообщений с неизвестным источником значение равно `null`. Например, условие `message.fromSource = 'PORTAL'` запускает ветку для сообщения из личного кабинета; для обработки именно события используйте `message`, поскольку `client.lastMessage` может уже относиться к более новому сообщению.

`client.messageFrom` задаёт основной канал клиента и также поддерживает `PORTAL`. Он может отличаться от источника конкретного сообщения. Для личного кабинета ответы сохраняются в общей истории и передаются через WebSocket без отправки во внешнюю систему.

- `data.*` получает данные, не принимает бизнес-решение.
- `list.select` отбирает, сортирует и ограничивает список. Текущий элемент — `var.item`. Условие отбора, сортировка и уникальность задаются скриптами с подсказками полей исходного списка: например, `var.item.createdAt` или `var.item.id`. Выражения для преобразования списка и описания вариантов Jev редактируются так же. Подсказка вставляется по Tab; поля старых графов вроде `createdAt` поддерживаются автоматически.

Редактор автоматически выводит типы переменных `var` из настроек, результатов операций, присваиваний и циклов. После фильтрации и объединения списков сохраняется тип элемента: для `var.matched` предлагаются `size()`, `first()` и `last()`, а после `var.matched.first().` — поля объекта. Для строк и дат доступны соответствующие методы. При изменении источника подсказки обновляются; неизвестный или противоречивый тип не считается списком автоматически.

- `list.project` получает значения полей списка; `list.concat` объединяет списки без одинаковых элементов.
- `ai.decide` возвращает `available`, `status`, `probability`, `choice` и `value`. Сам ничего не изменяет и не применяет порог.
- `task.update` принимает ID заявки, поэтому можно изменить найденную или созданную заявку, а не только заявку события.
- Настройки сценария по умолчанию находятся в `var.settings`.

В параметрах операций выражение хранится со знаком `=`, например `=var.recommendation.value.id`; визуальный редактор добавляет его сам. Текстовые подстановки записываются как `{{ var.recommendation.value.name }}`. В условиях и полях вычисления знак `=` в начале не нужен.

Пример результата выбора Jev:

```json
{"available": true, "status": "OK", "probability": 0.92, "choice": "2", "value": {"id": 2, "name": "Высокий"}}
```

Недоступный Jev возвращает `available=false`, а не положительное решение. Встроенное создание заявок имеет отдельную видимую запасную ветку для этого случая.

## Обработка нескольких объектов

«Для каждого элемента» имеет два выхода: «Элемент» и «Готово». Тело обработки должно доходить до выбранного блока «Следующий элемент». После всего списка выполняется «Готово». Блок «Остановить цикл» позволяет закончить список раньше.

Имя элемента, ограничение длины и сбор результатов настраиваются. Переменные элемента и индекса локальны для цикла. Вложенные циклы разрешены. Ожидания, фоновые операции и повторы с задержкой внутри тела запрещены: вынесите их за пределы обработки списка.

Встроенный сценарий создания заявок отдельно показывает сопоставление с открытыми заявками, выделение проблем по сервисам, проверку повторного обращения и создание непокрытых заявок. Исходное сообщение привязывается только к первой созданной заявке.

## Фоновые операции и подпроцессы

Фоновая операция сохраняет текущие данные и версию графа, ставится в очередь, а после получения результата продолжает ту же цепочку. Поэтому генерация выжимки статьи не задерживает обработку входящего сообщения. Число попыток и начальная пауза задаются в настройках операции; после исчерпания попыток работает выход «Ошибка».

Подбор статьи сохраняет ID, текст и клиента исходного входящего сообщения в `var.sourceMessage`. Выбор статьи и запрос генерации используют только этот текст, без истории переписки и прежних заявок. Явные шаги графа проверяют актуальность перед выбором статьи, перед объявлением о найденной статье и перед публикацией результата или ошибки. Если поступило новое входящее сообщение, устаревшая ветка завершается. Исходящие сообщения, комментарии, системные и удалённые сообщения не участвуют в проверке; порядок поступления определяется по ID, а не часам отправителя. Готовая подсказка содержит ID исходного сообщения.

В операции «Сообщения клиента» можно включить фильтр входящих сообщений и сортировку по ID. Фильтр применяется до ограничения количества записей. Дополнительный шаг отбора в графе показывает условия исключения служебных сообщений. Защита от повторов привязана к сообщению: новый вопрос может получить подсказку по той же статье. V67 обновляет сохранённые графы подбора статьи и сохраняет их прежние определения в `automation_workflow_backup`; настройки порогов остаются прежними.

Встроенный подпроцесс может иметь изолированные переменные, входы и выходы. На входе имя поля становится переменной дочернего сценария. На выходе имя поля — переменная родителя, значение — выражение из дочернего контекста. Асинхронный подпроцесс запускается отдельно и не возвращает немедленный результат.

## Проверка и журнал

Проверка не изменяет данные и не вызывает ИИ. Для узла анализа задайте «Пример ответа для тестирования». Без него проверка остановится на этом узле и сообщит, какие данные нужны. Можно проверить маршрут на заявке или передать JSON события, например событие Zabbix. Для шагов чтения и создания сущностей тоже можно задать тестовые результаты; это позволяет проверить детектор на вымышленных сигналах и пачках обращений без записи в базу. Для выбора Jev редактор предлагает варианты из входных данных предыдущей проверки. Примеры ответов не используются при реальном выполнении.

В трассировке каждого нового шага видны параметры, результат, переменные и выбранная ветка. Нажатие на название шага открывает его на холсте. История реального выполнения находится в «Журнал выполнения» в окне автоматизации. Ошибки и успешные операции сохраняются отдельно от транзакции маршрута.

«Журнал решений Jev» записывает каждый вопрос в запросе через общий клиент Jev. Для графа сохраняются сценарий, шаг, событие и связанные объекты; для ответа — выбор и уверенность, вероятность «Да» или числовая оценка. Ошибки API, некорректные ответы, отключённая интеграция и пропуски также видны. Полное состояние запроса в журнал не копируется.

Порога в журнале нет: один ответ может проверяться несколькими условиями графа с разными значениями. «Ответ получен» не означает выполнение действия — маршрут и применение ответа смотрите в журнале графа. Сводка группируется по сценарию и шагу, нажатие фильтрует именно этот шаг. Для прежних методов сохраняется их собственный итог проверки без дублирования строки запроса.

V66 восстанавливает пропущенные результаты `ai.decide` из имеющихся трассировок. Такие записи помечены «Из трассировки»; неизвестные идентификаторы событий и причины недоступности не восстанавливаются предположениями. Проигрывание квитанции операции и тестирование графа не создают новых запросов в журнале. Настройка `JEV_LOG_LEVEL` влияет только на вывод в серверные логи.

## Повторы и одновременные события

Изменение данных и запись результата операции выполняются в одной отдельной транзакции. Повтор той же операции возвращает прежний результат: заявка, заметка или уведомление не создаются второй раз. Для элементов списка используются стабильные ключи и сохранённый список, а не только позиция в текущей выдаче.

Для обработки событий одного сервиса встроенные графы Zabbix используют явную блокировку по ключу. Предложение статьи использует отдельную отметку «Выполнить один раз по ключу» для каждого входящего сообщения. Если исходный комментарий не удалось записать, видимая ветка ошибки снимает отметку и разрешает повтор.

## Миграция и прежние версии

V64 добавляет служебные таблицы и обновляет 12 встроенных сценариев. Прежние записи целиком сохраняются в `automation_workflow_backup`; они доступны в журнале сценария. Кнопка открытия прежнего графа загружает его в редактор для проверки — применение требует обычного сохранения.

V68 переносит конфигурацию от 20.10.2026: 18 автоматизаций и 5 папок, включая вложенность, порядок и свёрнутое состояние. Графы, параметры, описания и состояния активности берутся из снимка; счётчики и журналы существующих правил сохраняются. Папки сопоставляются по имени внутри родителя, правила — по имени, поэтому ID могут различаться между установками. Дополнительные пользовательские элементы остаются в своих папках после элементов снимка, а порядок выполнения пересчитывается по дереву. При неоднозначных одинаковых именах миграция останавливается с откатом. Прежние правила сохраняются в `automation_workflow_backup` с версией 68, дерево папок — в `automation_layout_backup`. Повторный запуск V68 не меняет уже перенесённую конфигурацию.

Действующие пороги Jev копируются в настройки новых графов. После переноса изменение глобальных порогов в настройках Jev не изменяет эти графы: редактируйте их блок «Настройки сценария». Прежние методы сохранены для совместимости там, где они существовали до переноса; новые встроенные графы их не используют как готовые бизнес-сценарии.

Источники шаблонов — `automation/templates/*.json`. Генератор `scripts/generate_automation_graphs.py` обновляет шаблоны и неприменённую V64 вместе. После применения миграции её нужно считать неизменяемой; последующие изменения поставляются новой миграцией.

## Границы ответственности

В графе находятся бизнес-условия, пороги, интервалы, выбор получателей, вопросы ИИ и последовательность действий. Серверные операции сохраняют проверки целостности, доступности сущностей, допустимости переходов, доставку сообщений и транзакционные гарантии. Новые комбинации доступных операций не требуют изменения движка; новый вид серверного действия добавляется в каталог операций.

Движок ограничивает граф 300 узлами, выполнение — 5000 шагами, вложенность — 8 уровнями, отдельный цикл — максимум 1000 элементов. Произвольные обратные связи запрещены; используйте цикл и настраиваемые повторы операции.
